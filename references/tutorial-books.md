## 1. 书籍与单篇教程的区别

单篇教程解决一个局部学习任务；一本书还必须管理知识依赖、长期记忆、节奏、重复、术语一致性和跨章节连接。

不要直接把多篇独立文章拼成一本书。先设计全书学习路线，再为每章选择 [tutorial-writing.md](tutorial-writing.md) 中的主结构。

一本教程书至少需要：

- 一个持续推进的核心问题、项目、对象或能力目标。
- 一个从读者起点到终点的知识依赖图。
- 一张会随着学习不断生长的全局地图。
- 可重复出现但逐步深入的实验、案例或作品。
- 统一的术语、图例、代码环境和叙述视角。
- 篇与章之间明确的能力交接。

## 2. 选择全书主线

根据读者和主题选择一种占主导地位的宏观结构。

| 全书主线 | 适用场景 | 组织方式 |
| --- | --- | --- |
| 自顶向下的对象旅程 | 普通初学者、开发者、复杂系统入门 | 从可观察事件出发，跟随请求、数据、任务或用户旅程，逐层放大 |
| 自底向上的系统搭建 | 工程专业、硬件、数学或需要严格依赖的主题 | 从基础构件开始，逐层组合成完整系统 |
| 项目成长 | 编程、设计、创作和工具使用 | 围绕一个持续生长的作品安排知识与练习 |
| 问题与故障 | 运维、安全、维修、临床式判断 | 围绕症状、证据、诊断与修复建立能力 |
| 概念地图 | 理论体系、跨领域入门 | 从少数核心概念扩展关系网络，并不断重组模型 |
| 故事或漫画 | 科普、低龄或强调记忆的主题 | 用持续角色和事件承载知识，但必须定期切回准确模型 |

不要平均混用多条全书主线。可以使用其他结构作为某一篇或某一章的局部形式。

## 3. 建立四层架构

### 整本书

定义读者从什么状态出发、最终能够解释或完成什么，以及贯穿全书的核心主线。

### 每一篇

用一个阶段性大问题、项目阶段或能力跃迁组织若干章节。篇名应表达读者能力的变化，而不是仅列学科名词。

### 每一章

从单篇规范中选择一种主要教学结构。不同章节可以分别采用链路追踪、原理图解、项目、对比、实验或排错。

### 每一节

只承担一个清晰认知动作：观察现象、完成动作、理解机制、比较差异、解释证据或修正模型。

## 4. 设计学习递进

### 先给可用模型，再逐步修正

第一次解释只提供当前阶段足够使用的模型。后续章节再次遇到该概念时，增加条件、内部机制和例外，并明确指出模型发生了什么变化。

不要在概念第一次出现时一次讲完所有细节。

### 管理知识依赖

- 为每章记录真正需要的前置概念。
- 如果一个概念必须提前使用，先提供临时模型，并承诺在明确位置展开。
- 避免“为了讲 A 先讲 B，为了讲 B 又先讲 C”的长前置链。
- 将查阅型细节、完整字段表和命令索引移入附录或参考部分。

### 控制认知负担

- 交替安排概念密集章与动手、案例或复盘章。
- 让读者早期获得一次完整但简化的成功体验。
- 每次只增加少数新角色，并把它们放回全局地图。
- 重复用于建立连接，不要原样复述定义。

## 5. 维持跨章节连续性

### 生长中的全局地图

序章给出刻意简化的全景。每学完一个重要模块，就在同一张地图上增加角色、关系、状态或例外。

### 持续对象或作品

优先让同一个请求、数据、项目、案例或角色贯穿多章，减少每章重新理解背景的成本。

### 术语账本

统一记录术语的首次正式定义、允许使用的简称、已废弃的临时类比和跨章引用。不要在不同章节为同一概念换用多个近义词。

### 类比账本

记录每个主要类比的对应关系和失效边界。后续进入准确模型后，明确停止依赖已经失效的类比。

### 统一视觉语言

为核心角色、层级、数据、控制信息、正常路径和异常路径使用一致的图形、颜色、线条与箭头。优先更新已有地图，不要每章重建视觉语法。

### 统一实验环境

尽量复用同一套项目、数据、工具和命令环境。环境发生变化时明确说明迁移原因和差异。

### 叙述声音连续性

- 全书保持稳定的称呼、叙述距离和专业密度，不要一章像聊天博客，下一章突然变成论文摘要。
- 序章或全书前言可以建立作者与读者的关系，普通章节不必重复打招呼、自我介绍和通用鼓励。
- 作者经历只在确实能推动当前认知动作时出现，并遵守 [tutorial-writing.md](tutorial-writing.md) 的真实性要求；不要为了维持“人设”给每章安排一次踩坑故事。
- 同一种口语过渡、玩笑或总结句不要跨章反复出现。书籍的熟悉感应来自稳定视角、持续项目和术语一致性，而不是重复口头禅。

## 6. 章节节奏与变化

多数章节可以围绕下列教学循环组织，但不要强制把它写成固定目录：

> 看见现象或结果 → 做一个小实验或预测 → 建立直觉 → 给出准确机制 → 验证 → 接回全书地图

根据章节目的改变节奏：

- 概念章可以从反常现象或问题开始。
- 项目章可以从新的可见里程碑开始。
- 链路章可以从一个对象进入系统开始。
- 排错章可以从症状和证据开始。
- 对比章可以从一个必须作出的真实决定开始。

篇末优先安排综合复盘、完整链路重放或阶段项目。练习不必每章都有，但应覆盖关键能力并提供判断标准。

## 7. 计算机网络示例

面向普通初学者和开发者时，优先采用“跟随一次网页请求和数据包旅行”的自顶向下主线。分层模型用于解释地图，不必成为全书从物理层到应用层的固定游览顺序。

一种可用的篇章规划是：

| 篇章 | 主要结构 |
| --- | --- |
| 序章：一次网页请求怎样完成 | 简化的完整链路追踪 |
| 应用与寻址：HTTP、DNS、IP 和端口 | 协议对话 + 查询旅程 |
| 可靠传输：TCP、UDP、丢包与拥塞 | 问题驱动 + 条件对比 |
| 跨网与局域网：路由、MAC、ARP 和 Wi-Fi | 数据包旅程 + 组件关系 |
| 安全：HTTPS 与 TLS | 攻击场景 + 原理图解 |
| 观察与排错：延迟、丢包和抓包工具 | 故障排查 + 可观察实验 |
| 终章：重新走完一次网页加载 | 完整链路复盘 |

这只是全书主线示例，不是固定目录。具体章节仍应根据当前问题选择查询旅程、协议对话、原理图解、实验、诊断树或条件化对比。

## 8. 全书检查

- 全书是否有一条可以用一句话说清的主线？
- 读者起点、终点和能力变化是否明确？
- 篇章顺序是否遵循学习依赖，而不是作者熟悉的学科目录？
- 序章是否尽早给出一个完整但简化的体验或模型？
- 每一篇是否解决一个阶段性大问题？
- 每一章是否选择了合适且单一的主要教学结构？
- 全局地图是否随着学习持续更新？
- 术语、类比、角色、代码环境和视觉语言是否跨章一致？
- 是否在必要时修正早期简化，而不是让临时模型永久存在？
- 概念密集内容与实验、案例、复盘是否形成节奏？
- 练习是否检验真实能力，并提供成功标准？
- 附录是否承接了查阅型细节，避免正文被字段和参数淹没？
- 终章是否让读者重新完成或解释全书最初提出的核心任务？
