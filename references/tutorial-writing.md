# 大白话教程写作规范

## 目录

## 1. 核心原则

- 让结构服从读者此刻的问题，而不是服从一套固定模板。
- 每篇教程只保留一条占主导地位的教学主线；其他结构只能作为局部辅助。
- 先让读者看见现象、结果或问题，再补充解释。避免长时间铺垫后才进入主题。
- 采用“观察或行动 → 建立直觉 → 给出准确模型 → 验证或应用”的教学循环，但不要把它强制写成固定小标题。
- 在读者刚好需要时解释概念。不要先倾倒完整理论，再开始实践。
- 大白话意味着降低理解成本，不意味着删除条件、边界和准确术语。
- 不要强制出现“适合谁、学完能做什么、生活类比、整体原理图、总结、练习题”等统一章节。

## 2. 选择主要教学结构

先识别读者的首要问题，再选择一种主结构。

| 读者的首要问题 | 主结构 | 自然骨架 |
| --- | --- | --- |
| 第一次接触，带我成功一次 | 首次成功型 | 成果预告 → 最小准备 → 一条受控路径 → 连续可见结果 → 简短回看 |
| 已经懂基础，怎么完成任务 | 任务完成型 | 目标与适用条件 → 必要前提 → 最短操作路径 → 就地验证 → 必要的例外、回滚或排错 |
| 想通过做出一个东西来学习 | 项目驱动型 | 成品预览 → 项目骨架 → 连续里程碑 → 按需解释概念 → 完成、部署或扩展 |
| 想知道它是什么、为什么存在 | 原理图解型 | 现实问题或现象 → 直觉模型 → 关键角色 → 工作机制 → 具体案例 → 边界与误区 |
| 想知道一次请求、消息或数据经历了什么 | 链路追踪型 | 触发事件 → 全景路线 → 跟随对象前进 → 逐层放大 → 异常或变化 → 拼回完整流程 |
| 东西坏了，应该查哪里 | 故障排查型 | 症状与复现 → 低成本检查 → 按结果分支 → 解释证据 → 修复 → 验证 → 预防 |
| A 和 B 应该选哪个 | 对比选型型 | 决策场景 → 比较标准 → 对称介绍 → 同一案例对比 → 权衡 → 按条件建议 |
| 需要练习而不只是阅读 | 互动练习型 | 一个微小概念 → 演示 → 任务 → 即时反馈 → 提示或答案 → 下一关 |
| 正在完成一门系统课程中的单元 | 课程单元型 | 学习目标 → 概念与应用递进 → 阶段练习 → 知识检查 → 与后续单元连接 |

若读者只是查找参数、语法、配置项或错误码，内容更接近参考文档，不要强行写成教程；退出本技能并按默认方式处理。

### 混合结构

- 可以在项目章节中嵌入一个短原理解释，也可以在链路追踪中嵌入局部对比。
- 不要把“概念、原理、实战、排错、总结”并列为五条同等主线。
- 判断冲突时，保留最能推动读者继续学习或行动的那条主线，其余信息就地嵌入或移至旁注、附录和链接。

## 3. 组织标题与段落

### 开头

根据主结构，从以下一种入口开始：

- 读者正在经历的真实问题或可观察现象。
- 本文将完成的具体作品或结果。
- 一个足以推动全文的问题。
- 一次即将被跟踪的请求、消息、操作或故障。

在开头自然交代必要的受众、前提和结果，不要默认把它们分别做成多个二级标题。

### 标题

优先使用：

- 读者下一步自然会问的问题，例如“浏览器怎么找到服务器？”
- 当前动作，例如“让服务器返回第一段内容”。
- 可观察里程碑，例如“棋盘现在可以响应点击了”。
- 诊断分支，例如“域名能解析，但 IP 仍然访问不了”。

避免“概念介绍、详细说明、核心内容、实战部分、其他知识、总结提升”等不能帮助读者定位进度的空标题。

### 信息位置

- 把命令的预期结果放在命令附近。
- 把错误排查放在容易发生错误的步骤附近；只有跨步骤问题才集中成排错章节。
- 把术语解释放在第一次真正需要该术语的地方。
- 把图放在读者需要建立模型、确认状态或比较差异的位置。
- 把背景历史留给确实能解释当前设计的场合。

## 4. 作者声音与真实性

### 默认声音

- 坦诚、克制、务实，像一位有经验的朋友陪读者一起完成任务，而不是站在讲台上炫耀知识。
- 有对话感，但不刻意装熟、撒娇、煽情或持续使用陪伴话术。专业内容仍以事实、机制和可验证结果为中心。
- 允许保留个人判断和经验感，但不要把固定口头禅、招呼语或自嘲变成每篇文章都必须出现的模板。
- 修改已有教程时，优先延续原稿已经形成的叙述距离、称呼方式和语气强度；除非用户明确要求，不要突然换成人设化文风。

### 第一人称与开篇

- 面向公众号、个人教程站等公开文章时，如果作者原有风格适合，可以自然打招呼或使用第一人称建立对话。
- 教程书章节、课程单元和内部知识库通常直接进入当前问题、现象或任务，不要每章重复自我介绍和招呼。
- 第一人称适合表达作者真实做过的动作、观察、判断和取舍；纯机制解释可以使用中性叙述，不必强行加入“我”。
- 开篇是否打招呼由媒介、原有声音和本章任务决定，不能成为统一模板。

### 经历、踩坑与案例真实性

- 只有用户明确提供，或现有原稿、日志、截图、提交记录、运行结果等材料能够支持时，才可以写“我踩过这个坑”“我当时怎么做”等作者经历。
- 助手在当前任务中亲自运行得到的结果，应写成“本次验证”“当前环境实测”或同等准确表述，不要改写成作者过去的亲身经历。
- 没有经历证据时，改写为“常见失败”“一个可以复现的问题”或“下面故意构造一个错误示例”，并明确其性质。
- 区分作者亲历、当前复现实验、行业常见问题和虚构或合成案例，不能把后面三类伪装成作者回忆。

### 去除机械的 AI 腔

- 检查重复模式，而不是封杀某一个句式。连续使用“不是 A，而是 B”、设问、自问自答、整齐排比、“首先/其次/最后”或相同长度的小节，会让文章显得机械；必要且准确时仍可正常使用。
- 段落过渡必须承担逻辑作用，例如承接前一步结果、提出新问题或说明因果。删除“接下来让我们看看”“相信你已经明白”等没有信息的过渡句。
- 结尾回到读者刚完成的任务、形成的判断或仍然存在的边界，不要使用通用鼓励、口号或与全文无关的升华。
- 幽默和自嘲只能偶尔使用，并且不能虚构经历、贬低读者或遮住真正的技术原因。

## 5. 大白话表达

- 使用常用、具体的词，但保留无法替代的技术术语。
- 第一次出现术语时说明：它是什么、在当前场景中负责什么、为什么现在需要它。
- 优先使用短而完整的因果句，避免连续名词和多层从句。
- 使用主动语态，明确谁做了什么。
- 禁止用“显然、只需、简单、大家都知道、毋庸置疑”等表达压低读者。
- 不要用拟人和俏皮话替代机制。它们只能辅助记忆，不能承担全部解释。
- 不要把“大白话”写成幼稚语气、网络段子堆积或过度热情的陪伴话术。

### 类比必须有退出通道

使用类比时完成三件事：

1. 说明类比中的角色分别对应真实系统的什么。
2. 用准确术语重新表述一次机制。
3. 指出类比在哪些地方不再成立，避免读者把辅助模型当成技术事实。

## 6. 示例、实验与反馈

- 示例服务于当前认知动作，不要为了显得丰富而加入无关示例。
- 代码、命令和配置应当完整、可运行，并注明适用版本、环境和文件位置。
- 无法实际运行的内容明确标记为伪代码、示意输出或概念模型。
- 每次操作后尽快提供可观察反馈：页面变化、终端输出、数据变化、测试结果或图中状态变化。
- 项目教程使用可工作的连续增量，不要让读者在多个章节后才第一次看到结果。
- 解释代码时优先说明为什么这样做、它改变了什么，以及不这样做会怎样；不要逐字翻译代码。
- 练习应检验刚建立的能力，并提供成功标准。只有课程、互动教程或用户明确要求时才加入练习。
- 写入 Markdown、MDX 或其他文件时，代码块应在语言明确时标注 `python`、`javascript`、`bash`、`json`、`yaml`、`text` 等类型；命令输出和伪代码也应使用准确标签。
- frontmatter、标题层级、内部链接、资源路径和发布格式服从当前仓库规范。仓库没有要求时，不要为所有教程强行添加同一种 frontmatter。
- 修改文件后检查本地链接、标题锚点和图片资源是否可解析，并执行仓库提供的文档构建、链接检查或格式验证；没有现成工具时，至少完成与改动范围相称的人工或脚本检查。

## 7. 图示路由

图必须承担理解、验证或决策作用。选择与认知任务匹配的形式：

| 需要理解的关系 | 图示形式 |
| --- | --- |
| 动作、调用或消息的先后 | 流程图或时序图 |
| 多个组件如何连接 | 架构图或组件关系图 |
| 状态如何变化 | 状态图或前后对比 |
| 一次数据、请求或对象的旅程 | 全景路线图，并在各阶段复用和高亮 |
| 软件界面操作 | 紧跟步骤的标注截图 |
| 抽象概念 | 先用类比插图建立直觉，再用技术图校正 |
| 两个方案的差异 | 同一案例的并排图或对比表 |
| 故障排查 | 诊断决策树与正常/异常输出对比 |
| 项目逐渐完成 | 各里程碑的效果图或状态快照 |

- 图前交代它要回答的问题，图后指出读者应该观察到的结论。
- 使用一致的角色、颜色、箭头和术语；同一套系统优先更新旧图，而不是每节重画一套视觉语言。
- 不要为“图文并茂”添加装饰图、无关封面图或重复正文的图。
- 若当前环境提供 Mermaid、Draw.io、截图、图像生成或交互可视化能力，按图的任务选择合适工具；不要为了调用工具而强行配图。

## 8. 条件模块

以下模块只有满足条件时才出现：

- **前置准备**：存在真实环境、权限、版本或知识依赖时。
- **风险与回滚**：操作危险、不可逆、涉及生产数据或可能中断服务时。
- **术语表**：术语很多且无法在正文中自然解释时。
- **集中排错**：问题跨越多个步骤或需要诊断树时。
- **FAQ**：有真实、高频且正文不便容纳的问题时；不要制造 SEO 式问答。
- **总结或回顾**：文章较长、模型复杂，或需要重新拼接完整链路时。
- **下一步**：存在明确且可靠的学习路径时。
- **练习题**：内容属于课程、互动学习或用户明确要求时。
- **参考资料**：需要给出事实来源、规范、版本文档或进一步阅读时。

## 9. 不同结构的收束方式

- 首次成功型：确认读者已经得到第一个可用结果，并说明刚才真正学会了什么。
- 任务完成型：给出验证标准；必要时补充回滚或维护提示。
- 项目驱动型：展示最终作品，说明各里程碑如何组合，并提供少量可选扩展。
- 原理图解型：回到开头的问题，用准确而简短的模型重新回答。
- 链路追踪型：从头到尾重放一次完整路径，突出各角色的交接关系。
- 故障排查型：确认症状消失，记录判断依据，并给出预防或取证建议。
- 对比选型型：输出按条件选择的判断规则，而不是宣布一个永远正确的赢家。
- 互动练习型：用系统验证结果结束当前关卡，并连接下一项能力。
- 课程单元型：说明该单元给后续学习增加了哪项能力。

不要求使用“总结”作为标题。

## 10. 交付前检查

- 是否明确了读者当前水平和学习结果？
- 是否只有一条主要教学主线？
- 标题是否反映问题、动作、里程碑或判断，而不是空泛分类？
- 是否在需要的位置解释术语，而非一次性倾倒？
- 类比是否映射回准确模型并说明失效边界？
- 作者声音是否适合当前媒介，并与已有内容保持一致？
- 第一人称经历和踩坑是否有真实材料支持，且没有把当前实验冒充作者回忆？
- 是否减少了重复句式、空过渡和通用结尾，而不是机械禁用正常表达？
- 示例、命令、代码和输出是否真实、完整、版本明确？
- 读者是否能定期获得可见反馈？
- 每张图是否减少了理解成本或帮助验证？
- 是否删除了没有触发条件的固定模块？
- 是否说明了重要限制、例外和不确定性？
- 文件格式、代码块语言、链接、锚点和资源路径是否符合当前仓库规范并已检查？
- 结尾是否与所选结构相匹配？
